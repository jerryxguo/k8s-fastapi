# k8s-demo-service

An example FastAPI service, deployed to AWS EKS, with a full Terraform +
Helm + GitHub Actions CI/CD pipeline -- **self-contained**: nothing in this
repo's pipeline depends on another repository. See `docs/DESIGN-NOTES.md`
for the key design decisions and rationale, and `docs/ARCHITECTURE.md` for
a component diagram.

## Repo layout

```
pants.toml           Pants build system config
src/                 Pants source root
  BUILD              python_requirements target parsed from requirements.txt
  requirements.txt   the one flat dependency list for this project's
                     single Pants resolve (app + test + lint/typecheck tools)
  requirements.lock  generated by `make lock` -- committed to git (CI has no
                     step that generates it, so it must already be present
                     for `pants lint`/`test`/`package` to resolve anything)
  app/               FastAPI application (generic example endpoints), plus
                     the BUILD file with its pex_binary + docker_image targets
                     and the Dockerfile Pants builds from
tests/               pytest suite, run via `pants test ::`
infra/terraform/     AWS account-level infra: VPC, EKS, ECR, IAM/IRSA
  modules/           reusable modules (this repo owns these outright --
                     nothing sourced from another repository)
  live/{dev,prod,shared}/   per-environment root modules -- "shared" owns
                     just the ECR repo + push role, nothing else runs there
infra/k8s/helm/      the Kubernetes-side deploy: Deployment/Service/
                     Ingress/HPA/ExternalSecret for this one service
.github/workflows/   pull-request.yml, release.yml, and the reusable
                     workflows they call
.github/actions/     composite actions (bootstrap-pants, build-version) --
                     inlined here rather than pulled from another repo
docs/                DESIGN-NOTES.md, ARCHITECTURE.md
```

## Local development

This project builds with [Pants](https://www.pantsbuild.org/) -- see "Build
tooling: Pants" in `docs/DESIGN-NOTES.md` for why. Install the Pants launcher
once per machine
(not part of this repo -- it self-bootstraps the exact version `pants.toml`
pins on first run):

```bash
curl -fsSL https://static.pantsbuild.org/setup/get-pants.sh | bash
# or: brew install pantsbuild/tap/pants
```

Then, from the repo root:

```bash
make lock      # whenever src/requirements.txt changes: pants generate-lockfiles
               # -- produces src/requirements.lock. Commit the result -- CI
               # has no step that regenerates it, it just expects it to
               # already be there.
make test      # pants test :: -- pytest, 85%+ coverage required
make lint      # pants lint check :: -- black/isort/flake8 + mypy
make fmt       # pants fmt :: -- auto-fixes black/isort
make run       # pants package src/app:docker, then docker run on :8080
```

```bash
curl localhost:8080/healthcheck
curl -X POST localhost:8080/v1/items -H 'content-type: application/json' -d '{"name":"widget"}'
curl localhost:8080/v1/items
```

## Deploying the infrastructure

Each environment is a separate AWS account: one account per environment,
one CI/CD IAM role per environment. Per environment:

```bash
cd infra/terraform/live/dev   # or prod / shared
cp terraform.tfvars.example terraform.tfvars   # fill in real values
terraform init      # after uncommenting the S3 backend in backend.tf
terraform plan
terraform apply
```

Apply `shared` first: it owns the single ECR repository that every
environment pulls the same image from (see "ECR strategy" in
`docs/DESIGN-NOTES.md`), and has no dependency on dev or prod. Then apply
`dev` and `prod`, passing the shared account's ID into each one's
`shared_account_id` tfvar.

Terraform CLI, AWS provider, and the `terraform-aws-modules` registry
modules could not be exercised in the sandbox this project was built in (no
network egress to `releases.hashicorp.com`/the module registry) -- every
`.tf` file was checked for syntax validity with `python-hcl2`, but you
should run `terraform init && terraform validate` (and ideally `plan`)
yourself before the first real `apply`. Same caveat for `helm lint` (no
`helm` binary in that sandbox either) -- templates were hand-reviewed and
brace/block-balance-checked instead; see `make helm-lint` once you have the
CLI. The Pants launcher itself (`static.pantsbuild.org`) was equally
unreachable from that sandbox, so `pants` was never actually run either --
every `pants.toml`/`BUILD` file was checked for valid syntax instead. Run
`make lock && make test && make lint && make build` yourself the first time
you clone this repo, before trusting CI to be green.

After `apply`, install the two cluster-wide add-ons this project's Helm
chart assumes exist (AWS Load Balancer Controller, External Secrets
Operator) -- see `infra/k8s/README.md`.

## Wiring up GitHub

Create three GitHub Environments -- `development`, `production`, `shared`
-- matching the `github_environment` each account's `cicd_role` module
trusts. For each, set:

| Name | Type | Value |
|---|---|---|
| `AWS_ROLE_ARN` | secret | that environment's `cicd_role_arn` Terraform output |
| `AWS_REGION` | variable | e.g. `ap-southeast-2` |
| `EKS_CLUSTER_NAME` | variable | that environment's `cluster_name` Terraform output -- **not applicable to `shared`**, which has no EKS cluster |
| `APP_IRSA_ROLE_ARN` | variable | that environment's `app_irsa_role_arn` Terraform output -- **not applicable to `shared`** |
| `ENVIRONMENT_SHORT` | variable | `dev` / `prod` (selects `values-<env>.yaml`) -- **not applicable to `shared`** |
| `ECR_REPOSITORY` | variable | **`shared` only** -- the `ecr_repository_url` output, e.g. `<shared-account>.dkr.ecr.ap-southeast-2.amazonaws.com/k8s-demo-shared/service-api` |

Add a required reviewer on the `production` Environment's protection rules
for a manual approval gate before production deploys -- that's where the
promotion gating lives (in GitHub's Environment protection rules, not in
workflow YAML).

## CI/CD

- **`pull-request.yml`** -- on every PR: lint + test, build + push (to the
  ECR repo owned by the `shared` account), deploy to `development`,
  smoke-test.
- **`release.yml`** -- on every merge to `main`: build once, then promote
  the identical image through `development → production`, smoke-testing
  after each deploy.

Full detail on why each of these looks the way it does is in
`docs/DESIGN-NOTES.md`.
