# Terraform gotchas specific to this project

## State only knows what it's told -- it doesn't detect reality on its own

`terraform plan`/`apply` compares the configuration against the *state file*, not against what's actually running in AWS. If a resource was created outside this exact state (manually, from a different machine's local state, or via a since-lost state file), Terraform has no idea it exists and will plan to create it again -- often failing with an "already exists" error from the AWS API rather than a clean diff. The fix is `terraform import` for each affected resource, one at a time, after confirming the AWS account/credentials in use match the resource's actual account (`aws sts get-caller-identity`).

`terraform apply -refresh-only` updates the *recorded* state to match real infrastructure but does not fix drift between configuration and reality -- it's for reconciling state with what's actually deployed, not for picking up config changes.

## Local state does not travel between machines

If Terraform state is local (the default, a plain file on disk), a second machine has no way to see changes applied from the first -- its `plan` will look like nothing has been applied yet, or (worse) will show a bogus diff trying to recreate everything. There is no way to make `plan` "aware" of another machine's local runs short of manually copying the state file over, which only works for one snapshot in time. The real fix is a remote backend (S3, with locking) so every machine reads and writes the same state, with locking to prevent two concurrent applies from corrupting it. This project uses Terraform's native S3 lockfile (`use_lockfile = true` in the backend block, Terraform 1.10+) rather than a separate DynamoDB lock table -- functionally the same guarantee, one less resource to bootstrap and pay for.

Bootstrapping that backend is a chicken-and-egg problem: the S3 bucket has to be created out-of-band (plain AWS CLI, once) before Terraform can be configured to use it as a backend. After uncommenting the backend block, use `terraform init -migrate-state` (not a plain `init`) so the existing local state gets copied up rather than starting fresh. One state bucket per AWS account is simpler than one shared bucket with cross-account bucket policies, if different environments live in different accounts.

Never commit the state file to git as a substitute for a remote backend: it routinely contains sensitive values in plaintext, git has no locking (two applies racing each other silently corrupt whichever commit loses), and large frequently-rewritten JSON files are a poor fit for git's merge model anyway.

## The S3 backend block needs its own literal `profile` -- it can't reference a variable

A `terraform { backend "s3" { ... } }` block is resolved before any variables are evaluated, so it can't reference `var.profile` (or any other variable) the way the `provider "aws"` block can -- it has to be a hardcoded literal string. If the backend block omits `profile` entirely, `terraform init`/`plan` falls back to whatever the ambient AWS credential chain resolves to (environment variables, the `default` profile, etc.), not the profile you're actually logged into via `aws sso login --profile <x>` -- which surfaces as a confusing credentials/expired-token error that has nothing to do with whether your SSO login actually succeeded. Fix: add `profile = "<the-same-value-as-this-environment's-var.profile-default>"` directly in the backend block, duplicating the literal rather than trying to share it with the provider block.

## EKS access entries: the principal ARN must be a real, assumable identity

An EKS access entry's `principal_arn` has to reference an IAM principal that can actually authenticate as itself -- a real IAM user or role ARN, not a fabricated ARN derived by hand from an assumed-role STS ARN, and not a placeholder/example value left over from a template. If this value is wrong, `terraform plan` shows the access entry (and its policy association) as needing replacement -- `-/+`, not a simple in-place update, because AWS's access-entry API can't mutate the principal, only delete and recreate. Applying that plan destroys the entry currently granting your own cluster-admin access and replaces it with one for a principal nobody can assume, locking you out of `kubectl` access to the cluster entirely. Always read a `-/+` diff on an access entry carefully before applying -- if the "current" principal shown in the diff is the one that's actually working today, the tfvars value is wrong, not the state.

## EKS Kubernetes version support windows

Keep `kubernetes_version` on whatever AWS currently has in standard support -- once a version's support window ends, its node-group AMIs stop being published, and `apply` starts failing with "Requested AMI for this version is not supported" even though nothing in the config changed. Check AWS's current EKS version support table before bumping. The rule that you can only upgrade one minor version at a time only applies to *upgrading* an existing cluster (`UpdateClusterVersion`) -- it is not a constraint on cluster creation. If you're destroying and recreating a cluster rather than upgrading it in place, you can jump straight to any currently-supported version.

## Cluster add-ons need their own IRSA role

An EKS managed add-on that talks to AWS APIs (for example a CSI driver) needs a dedicated IAM role bound to its own service account via IRSA -- without it, its pods come up but crash-loop with an `UnauthorizedOperation` calling whatever AWS API they need, because they're falling back to the node's own (much narrower) instance role. This is easy to miss because the add-on itself creates successfully; the failure only shows up once its pods actually try to run.

## GitHub OIDC trust subject must match exactly

The IAM role's OIDC trust condition compares the token's `sub` claim against a literal string built from the GitHub org/repo/environment -- if the org (or repo) is left at a placeholder/example value instead of the real one, the condition never matches the real token GitHub issues, and `sts:AssumeRoleWithWebIdentity` fails with `Not authorized`. Because this value has a natural-seeming default, it's easy to leave unset without Terraform ever complaining -- making it a *required* variable with no default turns a silent, only-visible-in-CI failure into a `plan`-time one. Also worth checking directly: a variable declared at the root of an environment doesn't automatically reach a child module just because both have a same-named variable -- it must be explicitly passed as an argument in the module block, and a missing pass-through silently falls back to whatever default the *module itself* declares, which may not be the one you think is in effect. Note also that this variable's name is a holdover from assuming a GitHub organization account -- for a personal GitHub account, the same field is just your username; the OIDC subject format (`repo:<owner>/<repo>:environment:<env>`) is identical either way.

## `sts:AssumeRoleWithWebIdentity` needs `sts:TagSession` too, if the CI action tags sessions

`aws-actions/configure-aws-credentials@v4` attaches GitHub context (repo, ref, sha, workflow, etc.) as IAM role session tags by default. When session tags are passed in the same call as `AssumeRoleWithWebIdentity`, STS requires the trust policy to *also* allow `sts:TagSession` for that principal -- a trust policy that only lists `sts:AssumeRoleWithWebIdentity` gets the whole call rejected with the same generic `Not authorized to perform sts:AssumeRoleWithWebIdentity` error, even though the `sub`/`aud` conditions match perfectly. This is easy to miss because the error text doesn't distinguish which permission was actually missing. Fix: add `"sts:TagSession"` alongside `"sts:AssumeRoleWithWebIdentity"` in the trust policy statement's `actions` list (same principal, same conditions). To isolate whether this is the cause without touching IAM, temporarily add `role-skip-session-tagging: true` to the `configure-aws-credentials` step -- if that makes the run succeed, this was it.

## GitHub's immutable OIDC subject claims (owner/repo numeric IDs) break trust policies written for the old plain-name format

Since GitHub's 2026-04-23 change, repositories created after 2026-07-15 automatically get OIDC tokens with *immutable subject claims*: the `sub` claim embeds the owner's and repository's permanent numeric IDs alongside their names, e.g. `repo:jerryxguo@10950337/k8s-fastapi@1337888631:environment:shared` instead of the old `repo:jerryxguo/k8s-fastapi:environment:shared`. A trust policy written against the old plain-name format never matches, and fails with the same generic `Not authorized to perform sts:AssumeRoleWithWebIdentity` -- with the trust policy, the OIDC provider, and the role ARN all otherwise looking completely correct, which makes this maddening to diagnose from the AWS side alone. The only way to know for sure is to decode the actual token: add a temporary workflow step that fetches the OIDC token via `$ACTIONS_ID_TOKEN_REQUEST_TOKEN`/`$ACTIONS_ID_TOKEN_REQUEST_URL`, base64-decodes its payload, and prints the real `sub`/`environment`/`repository` claims -- don't keep guessing from the trust policy JSON once `sts:TagSession` and everything else about the policy has already checked out. Once you have the real owner/repo IDs (`gh api repos/<owner>/<repo> --jq '.owner.id,.id'`), this project's `github-oidc-cicd-role` module accepts optional `github_owner_id`/`github_repository_id` variables that bake them into the trust condition to match. Older repos can also be opted into (or, per GitHub's docs, potentially back out of) this format via the org/repo-level OIDC customization API -- but matching the format Terraform-side is simpler and more future-proof than fighting GitHub's direction here, since immutable IDs also survive a future repo rename, unlike the plain-name format.

## Provider "Unrecognized remote plugin message" errors are usually environmental, not provider bugs

If every provider (including the simplest, most dependency-free ones) fails identically to load its schema with an error like "Failed to read any lines from plugin's stdout," that's a strong signal the problem isn't any one provider -- something is blocking the machine from executing freshly-downloaded plugin binaries at all. Check, in order: whether the binary has a quarantine/Gatekeeper-style flag blocking execution (macOS: `xattr -l <path-to-provider-binary>`, clear with `xattr -dr com.apple.quarantine <path>` if present); whether the download is simply corrupted (wipe the `.terraform` directory and reinitialize); and if neither resolves it, run the provider binary directly rather than through Terraform to surface the actual OS-level error, since Terraform's own error message here is a generic translation of whatever killed the process.
