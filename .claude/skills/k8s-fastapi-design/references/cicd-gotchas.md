# CI/CD gotchas specific to this project

## DECISION: the CI/CD role runs as cluster-admin, not AmazonEKSEditPolicy

This project originally scoped the CI/CD role's EKS access entry to `AmazonEKSEditPolicy` specifically so a compromised or misconfigured GitHub Actions credential couldn't touch cluster-scoped resources. In practice, that traded a one-time security decision for recurring, ongoing friction -- see the two gotchas below (namespace creation, then the `ExternalSecret` CRD) for two separate real incidents this caused, each requiring its own investigation and its own workaround. The pattern was structural, not a one-off: AWS's managed access policies are fixed and unextendable, so *any* new resource type a Helm chart or Terraform config needs to touch that isn't in Edit's fixed permission set would trigger the same class of error again, forever, one at a time.

The project has since moved the CI/CD access entry to `AmazonEKSClusterAdminPolicy` (`modules/eks-cluster/main.tf`), a deliberate, explicit trade: a compromised CI/CD credential now has real reach (read all secrets, delete nodes, disable the ALB controller, touch other namespaces), in exchange for CI/CD simply working without per-resource RBAC plumbing every time a chart changes. The gotchas below are kept because the underlying lesson (AWS access policies vs. native Kubernetes RBAC) is real and generally useful -- but this project itself no longer needs the group/ClusterRoleBinding workaround they describe, since cluster-admin already covers everything.

## Reusable workflow secret scoping

A job inside a *called* (reusable) workflow that declares `environment: <name>` does not automatically get access to secrets defined on that GitHub Environment, even when the reusable workflow lives in the same repository as the caller and is invoked by relative path. The caller also needs `secrets: inherit` (or to pass that specific secret explicitly) on the job that calls it -- without it, every environment-scoped secret silently resolves to an empty string inside the called workflow, which surfaces as something like "Credentials could not be loaded" from whatever action tries to use the secret, with no indication that the secret itself is the problem. This is easy to miss because adding the secret to the Environment in the GitHub UI looks like it should be sufficient, and nothing in the workflow YAML looks obviously wrong.

## GitHub Environment secrets vs. variables in printed workflow logs

An unset secret referenced in a workflow step's `with:` block renders as an omitted line in the printed log output, not as an empty-quoted value -- so a missing `role-to-assume: ${{ secrets.X }}` line in a run's log usually means the secret itself was never set on that Environment, not that the workflow forgot to reference it.

## Production approval gates live in Environment settings, not YAML

A required-reviewer approval gate before a production deploy is configured entirely in GitHub's own Environment protection rules (repo Settings -> Environments -> the environment -> Deployment protection rules), not via anything in the workflow file. A workflow job with `environment: production` does not pause for approval by default -- that only happens once a required reviewer is explicitly configured on that Environment. Don't assume a gate exists just because the job targets a production-sounding environment name.

## Diagnosing "could not load credentials" in an OIDC-based job

When `configure-aws-credentials`-style actions fail to load credentials in CI, check in this order: (1) is the relevant secret actually present in the printed `with:` block, or silently omitted (see above); (2) does the calling job have `secrets: inherit` if the failing step lives in a reusable workflow (see above); (3) does the IAM role's OIDC trust policy actually match the token's subject claim for this exact repo/org/environment. Each of these produces a similarly generic-sounding failure, so check them in order rather than assuming which one it is.

## `helm --create-namespace` still fails on RBAC even when the namespace already exists

It's tempting to assume `--create-namespace` is a harmless no-op once the target namespace already exists -- surely Helm checks first and only creates if missing? It doesn't work that way from the API server's perspective. Kubernetes authorizes a request by the *verb requested* (`create`) against the caller's RBAC grants *before* it ever evaluates whether the target object exists; `--create-namespace` issues an unconditional `create` call every time, so a role that isn't authorized to create namespaces gets rejected with `namespaces is forbidden: ... cannot create resource "namespaces" ... at the cluster scope` regardless of whether the namespace has existed for five minutes or five months. There's no client-side "check existence, skip create if found" fallback happening anywhere in this path.

## An EKS access entry's AWS managed policy (AmazonEKSEditPolicy etc.) is NOT the same object as Kubernetes' native `edit` ClusterRole -- extending one does nothing for the other

Installing an operator's CRDs (e.g. External Secrets Operator's `ExternalSecret`) does not, by itself, grant existing `edit`-scoped principals any rights over the new custom resource type. The natural-looking fix -- add a `ClusterRole` labeled `rbac.authorization.k8s.io/aggregate-to-edit: "true"` with a `rule` for the new API group/resource, since Kubernetes' aggregation controller merges any such ClusterRole's rules into the real `edit` ClusterRole -- **does not work for a principal whose only grant is an EKS access entry's AWS managed policy association**, and this is easy to get burned by because every symptom along the way looks like it's working: `kubectl get clusterrole edit -o yaml` genuinely shows the new rule merged in after applying it, yet `kubectl auth can-i get <resource> --as=<the-role-arn>` still says `no`, and CI still fails with the identical `is forbidden` error.

The reason: AWS's own docs state access policies like `AmazonEKSEditPolicy` are "a fixed, AWS-defined permission set... You can't modify the contents of an access policy." They resemble Kubernetes' built-in `edit`/`view`/`admin` ClusterRoles in spirit (same rough shape of permissions), but an access entry bound via `policy_associations` is authorized against AWS's own internal, static definition of that policy -- it never reads the cluster's actual `edit` ClusterRole object, aggregated or not. Extending the native object is real (verifiable with `kubectl get clusterrole edit`) but completely inert for this principal.

The actual extension point: an EKS access entry also supports `kubernetes_groups`, independent of its `policy_associations`. That's a genuine, separate authentication attribute -- the principal authenticates into the cluster carrying that Kubernetes group membership, and ordinary native RBAC (`ClusterRoleBinding`/`RoleBinding`) evaluates against it exactly like any other group, layered on top of whatever the AWS policy grants. So the working fix is: add `kubernetes_groups = ["some-group-name"]` to the access entry (`modules/eks-cluster/main.tf`'s `access_entries` map, per-entry), then bind a plain `ClusterRole` (no aggregation label needed) to that group with a `kubernetes_cluster_role_binding_v1` whose `subject { kind = "Group", name = "some-group-name" }`. Verify with `kubectl auth can-i <verb> <resource> --as=<principal-arn>` before trusting it -- that command is what caught the aggregation approach silently not working, well before another full CI round-trip would have.

This project hit it for real, back when the CI/CD role was still scoped to `AmazonEKSEditPolicy` so it couldn't touch cluster-scoped resources like `Namespace`, with the app's namespace created ahead of time by Terraform (`kubernetes_namespace_v1.app`) for exactly that reason. That scoping is history -- `modules/eks-cluster/main.tf` now grants the CI/CD role `AmazonEKSClusterAdminPolicy` (see the DECISION section at the top of this file) -- but Terraform still owns the namespace, and `--create-namespace` is still not passed. It's easy to reason "the flag is redundant now but harmless, leave it as a fallback" -- that reasoning is wrong for any identity that lacks create permission on namespaces; the flag doesn't become inert once the namespace exists, it keeps trying and keeps failing. The fix is to simply not pass `--create-namespace` in CI once something else (Terraform, in this case) guarantees the namespace's existence -- there's no safe halfway option where it's kept "just in case."
